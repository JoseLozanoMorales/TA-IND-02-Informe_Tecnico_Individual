\section{Resumen}

En esta práctica se implementó un prototipo de base de datos distribuida para las oficinas de Cuenca, Quito y Guayaquil del Banco del Austro. Cada sede utiliza una instancia independiente de PostgreSQL 16 desplegada mediante Docker. Una aplicación desarrollada con Spring Boot consulta los nodos y selecciona la ubicación de una cuenta a partir de su prefijo: 22 para Cuenca, 17 para Quito y 09 para Guayaquil.

La solución permitió comprobar la fragmentación horizontal, la transparencia de ubicación y la autonomía local. Las pruebas funcionales confirmaron la consulta correcta de saldos, las transferencias locales y entre sedes, la recuperación conjunta de nueve clientes y la entrega de respuestas parciales cuando uno de los nodos no está disponible.

\textbf{Palabras clave:} base de datos distribuida, fragmentación horizontal, PostgreSQL, Docker, Spring Boot, autonomía local.

\section{Introducción}

Una base de datos distribuida almacena información en varios nodos físicos o lógicos, pero busca ofrecer al usuario una vista unificada del sistema. Esta organización permite acercar los datos a las sedes que los utilizan, distribuir la carga y mantener operaciones locales cuando otro nodo no está disponible.

El caso propuesto representa tres oficinas del Banco del Austro. La información de cuentas y transacciones se separa por oficina, mientras que la aplicación cliente oculta la ubicación física de cada registro. El consumidor de la API utiliza una sola dirección y no necesita conocer qué instancia PostgreSQL atiende la petición.

\section{Objetivos}

\subsection{Objetivo general}

Implementar un prototipo de base de datos distribuida para consultar y transferir información bancaria almacenada en tres nodos PostgreSQL independientes.

\subsection{Objetivos específicos}

\begin{itemize}
  \item Desplegar los nodos de Cuenca, Quito y Guayaquil mediante Docker Compose.
  \item Aplicar fragmentación horizontal a cuentas y transacciones según su oficina.
  \item Configurar tres fuentes de datos en una aplicación Spring Boot.
  \item Enrutar las consultas mediante los prefijos 22, 17 y 09.
  \item Exponer endpoints REST para consultar saldos, clientes y realizar transferencias.
  \item Verificar la autonomía local mediante la interrupción temporal de un nodo.
  \item Retornar respuestas parciales cuando un nodo no esté disponible.
\end{itemize}

\section{Fundamentos de la distribución}

\subsection{Nodos y sedes}

Cada sede corresponde a un nodo PostgreSQL autónomo. Cuenca administra la base de datos \texttt{banco\_cuenca}, Quito administra \texttt{banco\_quito} y Guayaquil administra \texttt{banco\_guayaquil}. Los datos se almacenan en volúmenes separados para conservarlos aunque los contenedores sean detenidos o recreados.

\subsection{Estrategia de fragmentación}

La tabla \texttt{cuentas} se fragmenta horizontalmente por oficina. El nodo Cuenca acepta únicamente filas cuya oficina sea \texttt{CUENCA}; el nodo Quito aplica la misma regla con \texttt{QUITO}. Las restricciones \texttt{CHECK} protegen esta condición directamente en el motor de base de datos.

La solución está formada por tres contenedores PostgreSQL y una aplicación Spring Boot. Aunque los tres motores escuchan en el puerto interno 5432, Docker los publica en puertos diferentes de la computadora anfitriona.

\begin{table}[H]
  \centering
  \caption{Componentes y puertos utilizados}

    \toprule
    Componente & Dirección & Responsabilidad \\
    \midrule
    PostgreSQL Cuenca & \texttt{localhost:5442} & Cuentas con prefijo 22 \\
    PostgreSQL Quito & \texttt{localhost:5443} & Cuentas con prefijo 17 \\

Los puertos externos 5442 y 5443 siguen la alternativa indicada en la guía para equipos donde el puerto 5432 ya está ocupado por una instalación local de PostgreSQL. Guayaquil se publicó en el puerto consecutivo 5444. Los puertos internos de los contenedores no fueron modificados.

\section{Implementación}

\subsection{Despliegue de PostgreSQL}

El archivo \texttt{docker-compose.yml} declara los servicios \texttt{db-cuenca} y \texttt{db-quito}, sus credenciales académicas, volúmenes persistentes, scripts de inicialización y una red común. Los archivos \texttt{01\_schema.sql} crean la estructura y los archivos \texttt{02\_datos.sql} insertan los registros de prueba.

\subsection{Configuración de Spring Boot}

La clase \texttt{DataSourceConfig} construye tres objetos \texttt{DataSource}. La configuración de conexión se encuentra en \texttt{application.yml}. El servicio \texttt{ConsultaDistribuidaService} crea un \texttt{JdbcTemplate} por sede y selecciona uno mediante los dos primeros caracteres del número de cuenta.

El proyecto fue configurado en IntelliJ IDEA con Microsoft OpenJDK 21.0.11 y nivel de lenguaje 21, de acuerdo con los requisitos establecidos para la práctica.

\evidencia{08_configuracion_jdk21.png}{Configuración del proyecto con JDK 21 y nivel de lenguaje 21 en IntelliJ IDEA.}{jdk21}

\subsection{Justificación de diferencias respecto a la guía}

La implementación conserva el comportamiento y los resultados solicitados en la guía, pero introduce pequeñas refactorizaciones para evitar configuración redundante y aprovechar las capacidades de Java 21. A continuación se justifican las diferencias principales.

\subsubsection{Propiedad del controlador en \texttt{application.yml}}

El listado de la guía incluye la propiedad \texttt{driver-class-name:}\allowbreak\ \texttt{org.postgresql.Driver} para cada fuente de datos. En este proyecto dicha línea se omitió porque \texttt{DataSourceConfig} establece explícitamente el mismo controlador mediante \texttt{driverClassName(}\allowbreak\texttt{"org.postgresql.Driver"}\allowbreak\texttt{)} al construir los tres objetos \texttt{DataSource}. La clase del controlador está disponible gracias a la dependencia de PostgreSQL declarada en Maven.

La configuración utiliza el espacio de propiedades personalizado \texttt{datasources} y no la configuración automática singular \texttt{spring.datasource}. Además, \texttt{DataSourceConfig} inyecta únicamente URL, usuario y contraseña. Por ello, añadir \texttt{driver-class-name} al YAML sin inyectarlo también en la clase dejaría una propiedad no consumida. Su omisión evita duplicar una configuración que ya se aplica de forma centralizada y no altera las conexiones comprobadas con Cuenca, Quito y Guayaquil.

\subsubsection{Refactorización de \texttt{DataSourceConfig}}

La guía inyecta URL, usuario y contraseña en campos de la clase y repite la construcción de cada fuente de datos. La versión implementada recibe esas propiedades directamente como parámetros de los métodos \texttt{dsCuenca}, \texttt{dsQuito} y \texttt{dsGuayaquil}. De esta manera, las dependencias de cada bean quedan visibles en su declaración y no se requieren campos mutables de configuración.

La lógica compartida se trasladó al método privado \texttt{construir}, que configura URL, credenciales, controlador y tiempo de espera en un único lugar. Esta decisión reduce duplicación: cualquier modificación común a las tres conexiones se realiza una sola vez. Los beans \texttt{dsCuenca} y \texttt{dsQuito} conservan los nombres de la guía y se añadió \texttt{dsGuayaquil} para el ejercicio propuesto.

\subsubsection{Refactorización de \texttt{ConsultaDistribuidaService}}

El servicio conserva las mismas consultas SQL y las reglas originales de enrutamiento: prefijo 22 para Cuenca y prefijo 17 para Quito. Se añadió el prefijo 09 para Guayaquil. La respuesta de \texttt{consultarSaldo} se expresa mediante un operador condicional en lugar de un bloque \texttt{if}. Cuando la consulta no devuelve filas se construye el mismo mapa de error; cuando existe una fila se retorna el primer resultado.

La guía obtiene esa fila con \texttt{get(0)}, mientras que la implementación usa \texttt{getFirst()}. Este método forma parte de la API disponible en Java 21, versión exigida por la práctica, y expresa directamente la intención de recuperar el primer elemento. También se escribió la consulta SQL como una sola cadena en vez de concatenar dos fragmentos. Estas diferencias mejoran concisión y legibilidad sin modificar el resultado funcional.

Después de la prueba, Quito fue iniciado nuevamente y recuperó su operación normal.

\section{Resultados de los ejercicios propuestos}

\subsection{Ejercicio 1: nodo Guayaquil}

Se añadió el servicio \texttt{db-guayaquil} a Docker Compose, con la base de datos \texttt{banco\_guayaquil}, un volumen independiente y publicación en el puerto 5444. Los scripts SQL crean las mismas tres tablas y restringen el fragmento mediante \texttt{CHECK (oficina = 'GUAYAQUIL')}. La aplicación incorporó el bean \texttt{dsGuayaquil} y la regla de enrutamiento para cuentas con prefijo 09.

El nodo inició correctamente con tres clientes y tres cuentas. La consulta de \texttt{0901000001} devolvió HTTP 200, saldo 12500.00 y oficina \texttt{GUAYAQUIL}.

\evidencia{09_guayaquil_activo.png}{Los tres nodos PostgreSQL en ejecución, incluido Guayaquil en el puerto 5444.}{guayaquil-activo}
\evidencia{10_saldo_guayaquil.png}{Consulta de saldo enrutada al nodo Guayaquil mediante el prefijo 09.}{saldo-guayaquil}

\subsection{Ejercicio 2: transferencias}

Se implementó \texttt{POST /api/banco/transferencia}, que recibe las cuentas de origen y destino junto con un monto positivo. El débito utiliza una actualización condicionada por el saldo disponible, evitando que una cuenta quede con valor negativo. Las transferencias dentro de una misma sede se ejecutan mediante \texttt{TransactionTemplate}, de modo que débito, crédito y registro del movimiento se confirman o revierten como una sola unidad.

La prueba local transfirió 25.01 desde \texttt{2201000001} hacia \texttt{2201000002}. La API devolvió estado \texttt{COMPLETADA}, tipo \texttt{LOCAL} y los saldos resultantes de ambas cuentas.

\evidencia{11_transferencia_local.png}{Transferencia completada entre dos cuentas del nodo Cuenca.}{transferencia-local}

Para cuentas de sedes diferentes se valida primero la existencia de ambos extremos, se ejecuta el débito en el nodo de origen y después el crédito en el destino. Si el crédito falla, la aplicación realiza una operación compensatoria que devuelve el monto al origen. La prueba transfirió 20.02 desde Quito hacia Guayaquil y devolvió estado \texttt{COMPLETADA} con tipo \texttt{ENTRE\_SEDES}. Después de verificar el resultado se ejecutaron operaciones inversas y se confirmaron nuevamente los saldos iniciales.

\evidencia{12_transferencia_entre_sedes.png}{Transferencia completada entre los nodos Quito y Guayaquil.}{transferencia-sedes}

La compensación implementada permite manejar fallos comunes en el prototipo, pero no ofrece las mismas garantías que un protocolo de commit en dos fases. Una interrupción extrema durante la compensación todavía requeriría conciliación manual o infraestructura distribuida adicional.

\subsection{Ejercicio 3: fallback de clientes}

El método \texttt{listarTodosLosClientes} consulta cada nodo de manera independiente y captura los errores de acceso. Con todos los nodos activos devuelve nueve clientes. Para comprobar el fallback se detuvo Guayaquil: el endpoint continuó respondiendo con HTTP 200, retornó los seis clientes disponibles de Cuenca y Quito, incluyó \texttt{GUAYAQUIL} en \texttt{nodosNoDisponibles} y añadió la advertencia de que la respuesta era parcial. Finalmente, el contenedor fue restaurado.

\evidencia{13_fallback_clientes.png}{Respuesta parcial de clientes con Guayaquil temporalmente fuera de servicio.}{fallback-clientes}

Después de la prueba, el nodo Guayaquil fue reactivado. Los tres contenedores volvieron a mostrarse en ejecución y el endpoint de clientes respondió con HTTP 200, nueve registros, una lista vacía de nodos no disponibles y ninguna advertencia. Esto confirma que el sistema recuperó su operación completa sin reiniciar la aplicación.

\evidencia{13.1_reactivacion.png}{Reactivación de Guayaquil y recuperación de los nueve clientes del sistema.}{reactivacion-guayaquil}

\section{Análisis de resultados}

Los resultados demuestran transparencia de ubicación porque el consumidor siempre consulta la misma API. La selección del nodo ocurre internamente y depende del prefijo de la cuenta. También se comprueba la disjunción de los fragmentos: cada sede acepta únicamente cuentas asociadas con su oficina.

La caída de un nodo no impidió consultar cuentas de las sedes disponibles, lo que evidencia autonomía local. El fallback añadido evita que el endpoint de clientes falle completamente: devuelve los registros recuperables y señala expresamente las sedes no disponibles. Un patrón Circuit Breaker podría complementar esta solución para evitar intentos repetidos contra un nodo que permanece caído.

\section{Conclusiones}

\begin{enumerate}
  \item Se desplegaron correctamente tres motores PostgreSQL independientes y persistentes.
  \item La fragmentación horizontal permitió asignar las cuentas a una sede mediante restricciones verificables en la base de datos.
  \item Spring Boot ofreció transparencia de ubicación al concentrar el acceso en una sola API REST.
  \item Las consultas de Cuenca, Quito y Guayaquil devolvieron los saldos esperados y la consulta conjunta recuperó nueve clientes.
  \item La prueba de fallos confirmó que un nodo disponible puede continuar atendiendo sus datos locales cuando el otro se encuentra detenido.
  \item Las transferencias locales y entre sedes actualizaron correctamente los saldos y las pruebas dejaron los valores iniciales restaurados.
  \item El fallback permitió entregar seis clientes y una advertencia durante la caída controlada de Guayaquil.
\end{enumerate}

\section{Recomendaciones}

\begin{itemize}
  \item Evaluar un coordinador distribuido o commit en dos fases para ofrecer atomicidad estricta entre sedes.
  \item Implementar un Circuit Breaker para evitar esperas repetidas ante fallos de conexión.
  \item Evaluar replicación lógica para información que deba estar disponible en todas las sedes.
  \item Utilizar variables de entorno o secretos para administrar credenciales en ambientes no académicos.
\end{itemize}
